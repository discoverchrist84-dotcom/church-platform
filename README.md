# Christ Ascension Church 1984 Foundation Constitution (Lifters Power Assembly)

A web platform for one church with many branches: a sourced history of the church, a space for every branch (announcements, events, sermons, board, groups, prayer wall), online giving, live notifications, light/dark mode and an installable mobile app (PWA).

**Stack:** Django 5 · Django Ninja (API) · PostgreSQL · Channels + Redis (WebSockets) · Celery · vanilla JS/CSS.

## Quick start

Use **Python 3.10 – 3.13** (3.12 is ideal). Very new Python versions often lack prebuilt packages.

### Windows (PowerShell, e.g. the VS Code terminal)

Run these one at a time from the project folder:

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1          # if blocked: Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
python -m pip install -r requirements/dev.txt
Copy-Item .env.example .env
(Get-Content .env) | Where-Object { $_ -notmatch '^(DATABASE_URL|REDIS_URL)=' } | Set-Content .env   # use SQLite
python manage.py makemigrations accounts churches history community media_library giving realtime
python manage.py migrate
python manage.py seed_demo            # optional sample data
python manage.py import_stations      # the church's 33 districts and 175 stations (safe to re-run)
python manage.py createsuperuser
python manage.py runserver
```

### macOS / Linux

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements/dev.txt
cp .env.example .env     # delete the DATABASE_URL / REDIS_URL lines to use SQLite
python manage.py makemigrations accounts churches history community media_library giving realtime
python manage.py migrate
python manage.py seed_demo && python manage.py createsuperuser
python manage.py runserver
```

Open http://127.0.0.1:8000 · admin at `/admin/` · API docs at `/api/docs`.

> **Upgrading from an earlier copy?** Replace the project files, keep your `.venv`, `.env`, `db.sqlite3` and existing `migrations/` folders, then run `python manage.py makemigrations community` and `python manage.py migrate` (this adds the `Report` table).

### Docker (Postgres + Redis + worker)


## Branding & appearance

- Name, short name and header lines are set in `config/settings/base.py` (`SITE_NAME`, `SITE_BRAND`, `SITE_SUBBRAND`, `SITE_SHORT_NAME`) and can be overridden in `.env`.
- **Your logo:** replace `static/img/logo.svg` (keep the name), or add e.g. `static/img/logo.png` and set `SITE_LOGO=img/logo.png` in `.env`. The home-screen/app icons are generated by `python scripts/make_icons.py` (edit the colours there, or drop your own PNGs into `static/icons/`).
- Colours live at the top of `static/css/app.css` (navy, blue, sky blue and gold). Visitors choose **Light, Dark or Match my device**; the choice is remembered in their browser.
- Set `TIME_ZONE` in `.env` (e.g. `Africa/Lagos`) so event times display correctly.

## What's included

- **History:** eras, events, figures, places, sources, documents; draft → review → published workflow in the admin; timeline, detail pages and search.
- **Branches:** nestable (headquarters → region → local); join/leave; roles (member / leader / admin). A parent branch's admin manages everything beneath it.
- **Public per branch:** announcements, events with RSVP, sermons (audio, video, PDF, or a pasted YouTube/Vimeo link).
- **Members only per branch:** community board with comments, groups/ministries, prayer wall (anonymous option).
- **Leaders:** post announcements, create events, add sermons, hide content, and review member reports (`Manage` tab).
- **Giving:** `/give/` with preset amounts, funds (church-wide or per branch), receipts by email, giving history. `PAYMENT_PROVIDER=dummy` simulates payments in DEBUG only.
- **Notifications:** live toast + header badge over WebSockets; a notifications page.
- **PWA:** installable, offline fallback page; personal pages are never cached on the device.

## Before going live

- Set a real `SECRET_KEY`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS`, and use `config.settings.prod`.
- Replace the demo history text with properly sourced content.
- Implement a real payment provider in `apps/giving/providers.py` (Stripe / Paystack / Flutterwave), verify webhook signatures there, and set `DEFAULT_CURRENCY`.
- Configure S3-compatible storage (`AWS_*`) so uploads aren't on the app server's disk.
- Add a privacy policy and agree a moderation process for the community features.

## Share the dev site on your Wi-Fi (LAN)

```powershell
python manage.py runlan
```

It prints two addresses. Open the second one (`http://192.168.x.x:8000`) on a phone or another computer **on the same Wi-Fi**.

- **Windows asks about the firewall** the first time: choose *Private networks* → *Allow*. If you missed it: Windows Security → Firewall → *Allow an app* → Python.
- It is plain HTTP, so use test data only. Phones also won't offer **Install app** or offline mode over plain HTTP (browsers require HTTPS or `localhost` for that); test installation on the live HTTPS site.
- Different network, or it still won't load? Check the phone is not on guest Wi-Fi/mobile data, and that your router doesn't isolate clients.

## Security: what is and isn't "encrypted"

| Protection | Where |
|---|---|
| **Traffic encryption (HTTPS/TLS)**: set up on the server, not in Django. `config.settings.prod` redirects to HTTPS, marks cookies secure and sends HSTS for a year. Put the site behind Nginx/Caddy/Cloudflare with a certificate (Let's Encrypt is free). Without this, nothing is encrypted in transit. | prod.py |
| **Passwords** are stored hashed (PBKDF2-SHA256), never readable. | Django |
| **Brute-force & spam limits**: per-IP request limit, a strict limit on sign-in/sign-up/giving forms, and a 15-minute block after 6 wrong passwords. Returns HTTP 429. | `apps/core/security.py` |
| **Browser protections**: Content-Security-Policy (only our own scripts run), no framing (clickjacking), no MIME sniffing, strict referrer and permissions policies, HttpOnly + SameSite cookies, CSRF tokens on every form. | `apps/core/security.py`, settings |
| **Uploads**: size caps, file-type checks, safe video-embed whitelist. | settings, `media_library` |

Honest limits: no website is "un-hackable". Rate limits stop casual spam and password guessing, not a large distributed attack. For that, put the site behind Cloudflare (free tier) and keep Django and the packages updated (`pip list --outdated`). Use Redis (`REDIS_URL`) in production so limits are shared between server processes. Back up the database. Never commit `.env`.

## Church structure and the General Council

**Structure:** Headquarters › Area › District › Station. In the admin (Churches › Branches) pick the *level* and the *parent*: an Area goes under Headquarters, a District under an Area, a Station under a District. The admin refuses any other arrangement. Admins of a higher unit can manage everything below it. The public **Structure** page shows the whole tree and can be filtered by level.

**Leadership:** In the admin open *Leadership & councils › Councils*, add "General Council" (leave *Branch* empty for church-wide) and add members inline with photo, title, bio and years served. Councils can also be attached to any area, district or station and then show on that unit's page. Email/phone are hidden unless you tick *Show contact*.

Upgrading from the previous version:
```powershell
python manage.py makemigrations churches leadership
python manage.py migrate
python manage.py seed_demo
```
Existing "Region" units become **Area** and existing "Local" units become **Station**. A station that sits directly under headquarters must be moved under a district in the admin before it can be saved again.


## Testing on your phone through a hotspot

`python manage.py runlan` prints every address your computer has. Open the one on the network your phone shares.

**A. Phone shares its hotspot (easiest):** turn on the phone's hotspot, join it from the computer, run `runlan`, then open the `http://172.20.10.x:8000` / `192.168.43.x:8000` address in the phone's browser (type it in the phone's address bar; the phone is the hotspot so it shares the same network).
**B. Computer shares a hotspot:** Windows Settings → Network → Mobile hotspot → On, join it from the phone, run `runlan`, and open `http://192.168.137.1:8000` on the phone.

If it will not load: run `scripts\allow_dev_firewall.ps1` once in an **Administrator** PowerShell (hotspots count as "Public" networks, which Windows blocks). Also check the phone isn't on mobile data / VPN.

## Structure rules (v5)

- There is exactly **one National Headquarters station** (enforced in the admin and the database).
- **Area** → top level (no parent). **District** → under an area. **Station** (a local church) → under a district. The **National Headquarters** is not a separate level: it is one station (tick *National Headquarters* on it; Ehi Road Station, Aba South District).
- **Area and District Superintendents:** open the area/district in the admin and add a *Leader* with role *Superintendent* (one serving at a time; tick *current* off when they step down). Stations get a *Pastor-in-charge*. Link a leader to a user account and they automatically become admin of that unit and everything below it.
- **National councils and their offices** (General Overseer, Secretary, Treasurer, PRO…) are in *Leadership & councils*.
- **Directory:** *Our structure* has a Tree view and a sortable Directory view (click any column), with filters by type, area and district, search (also by superintendent's name) and pages.
- Sign-in and sign-up have a show/hide password button. The admin is themed navy and gold.

Upgrade: `python manage.py makemigrations` then `python manage.py migrate` (no app names needed), then `python manage.py seed_demo`.

## The administration area (`/admin/`)

Sign in with the account from `createsuperuser`. The **dashboard** groups everything by what you want to do:

| Section | What you manage |
|---|---|
| Church structure | National Headquarters, areas, districts, stations, their superintendents and pastors, who belongs where |
| National councils | The General Council and others, with photos and offices |
| Community life | Announcements, events (with RSVPs), ministries |
| Moderation | Member reports, board posts, comments, prayer requests |
| Sermons & media | Sermons and uploaded files |
| Church history | Timeline events, eras, people, places, documents, sources |
| Giving | Funds and every gift |
| **Website settings** | **Site name, logo, announcement banner, contact details, social links, welcome line (no code needed)** |
| People & access | Accounts and roles |

**Add / edit / delete.** Every list has *Add* at the top right; click a name to edit; delete from inside the item (red button) or with the *Action* menu. Delete always asks you to confirm and lists what else would go. To take something off the site without losing it, untick *Active/Published* or tick *Hidden*. Every list also has **Download selected as a spreadsheet (CSV)** in the Action menu, and a *Needs your attention* box on the dashboard (open reports, areas without a superintendent, draft history, pending gifts).

**Who can do what.** On *People & access → Users* tick someone and choose an action:

| Role | Can do |
|---|---|
| Full administrator (superuser) | Everything, including who else is an administrator |
| Church administrator | Everything about the church: structure, content, people, giving, website settings |
| Content editor | Add and edit news, events, sermons, history, councils, leaders (never delete) |
| Moderator | Review posts, comments, prayer requests and reports |

You cannot lower your own access or deactivate yourself. After pulling new code run `python manage.py makemigrations` and `python manage.py migrate`; the roles are created and refreshed automatically.
